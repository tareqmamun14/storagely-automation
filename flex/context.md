## 1. Mission

Build the verification backbone for **Flex / V4**, Storagely's site builder. V4 lets designers compose pages from components (Heading, Modern Unit Card, Reviews, etc.) and **template tokens** like `{v2_api_location_units.width}` that resolve at render time against live API data.

Two surfaces:
- **Editor**: `https://sites.apps.mystoragely.com/editor/...` — where designers author pages.
- **Published live site**: `https://safeguard.test.getstoragely.com/...` — what the customer sees, rendered from the editor's saved config + real API data.

V2 has its own existing Playwright/TypeScript suite for rental checkout — DO NOT re-test it. We only need V4 to hand off to it cleanly via the Rent Now URL.

## 2. The strategic context from the CTO (Matt) — read carefully, this reframes everything

Matt's reply when shown an initial plan focused on editor + binding tests:

> *"Yep this is expected, I think a lot more testing on the E2E side is probably where a lot of things will be needed from this. B/c all the code is shifting up, eventually there will be zero code deployments to launch a site."*

**Interpretation — this is the load-bearing paragraph of this whole brief:**

V4 today is "a feature." Matt's roadmap has V4 becoming **the entire product launch pipeline.** Today, launching a new storage-facility site requires code + config; tomorrow, it will require config only. *The configuration IS the product.*

Implications for the test strategy:

1. **The test suite is not testing a tool. It is the verification backbone for a no-code product pipeline.** Frame all decisions through this lens.
2. **Layout will vary site-to-site based on configuration.** Selector-rigid Playwright tests will rot fast — every config tweak will break tests that hardcode CSS structure.
3. **E2E customer journeys are the priority, not editor mechanics.** Editor smoke is foundation; the headline is "a customer can browse → pick a unit → start renting" on any published site, regardless of which template generated it.
4. **Lean toward semantic, layout-tolerant, agent-driven verification.** Find elements by role + visible text + accessible name, not by CSS path. Pair with LLM-as-judge passes for "does this page look broken" — this is now Phase 1, not Phase 2.

If a design decision has to choose between "fast/deterministic but brittle to config variation" and "slightly slower but layout-tolerant," pick the latter. The whole product is about to be layout-variable.

## 5. Architectural decisions already made

- **Manifest-driven.** Tests loop through YAML; never hardcode. `kind` field on a property tells the generator which test pattern to emit (checkbox/select/text/binding).
- **Skill files = stable knowledge.** Selectors, helpers, action patterns live in `.claude/skills/`. Tests pull from there. This is the anti-flake layer.
- **Cross-origin renderer iframe.** Preview is at `sites-frame.apps.mystoragely.com` — every preview-side assertion must go through `frameLocator()`. See `helpers/frame.ts`.
- **Page-object pattern.** `page-objects/editor/EditorPage.ts` is the only file that knows how to drive the editor.
- **Auth captured once.** `tests/global.setup.ts` logs in via `EDITOR_USER_EMAIL` / `EDITOR_USER_PASSWORD` env vars and stores `fixtures/auth/editor-storage-state.json`.
- **Three Playwright projects.** `editor` (uses storage state), `live` (no auth), `bindings` (no auth, runs against live URL).

If you want to change any of these, do it deliberately and update the SKILL.md files.

## 8. New verticals to explore — Matt-aligned, your call on prioritization

Matt didn't prescribe specifics; he prescribed direction. These are the verticals that follow from "zero code deployments + E2E focus":

- **E2E customer journeys** — `tests/e2e/*.spec.ts`. Land on facility page → browse units → pick one → click Rent Now → land on V2 checkout with correct unit_id. Use semantic locators (role + visible text) so it survives layout variation.

  Design challenge: how do you write ONE journey spec that runs against multiple facility configurations? The journey is the constant; the page layout is the variable. Think `journey-driver(facility)` — parameterized by `manifests/facilities.yaml`.

- **Configuration variation matrix** — pick the same journey, run it against N facilities each with different builder configs (different layouts, different visible components). The test passes if the journey completes regardless of config.

- **LLM-as-judge visual sanity** — after each E2E test reaches a published page, take a screenshot, ask a model "is this a working storage facility listing page or does it look broken?" Catches the long tail of regressions exact-pixel tests can't (because layout varies) and selector tests miss (because each selector individually passed).

- **Publishing pipeline verification** — config saved in editor → live URL reflects within SLA. Test the deploy itself, not just the rendered output. Critical for "zero code deployments" — the deploy IS the release.

- **Multi-tenant variation** — different tenants (Safeguard vs. others) have different brand configs. One journey across all of them is the smoke test for the no-code pipeline as a whole.

- **Empty-state coverage at scale** — facilities with zero units, zero reviews, zero images. Easy to break, easy to miss.

- **Regression replays** — when a bug ships, capture a focused spec in `tests/regression/{ticket-id}.spec.ts`. Permanent guard against recurrence.

- **Performance budgets on published pages** — LCP, CLS, etc. Customers convert worse on slow pages. Builder-induced layout shifts (CLS regressions) are a real risk in a config-driven world.

- **Accessibility audits on published pages** — axe-core run per facility, fail on violations. Often the first thing config-driven products regress on.

You don't need to build all of these. Pick the 2–3 that most directly land Matt's stated priority (E2E + zero-code-deploy resilience), build them well, and document the rest in a roadmap.

## 10. Working norms from the prior session — keep these

- One prompt → one spec. Don't ask a generator to test "the whole page."
- Skill files own selectors. Tests must not invent selectors.
- The manifest is the source of truth. If you discover a new component or token in the editor, update the manifest *first*, then run the generator.
- Editor tests collide on shared state. Run serially (`workers: 1`) or parameterize the `?path=` URL per test.
- Stop at the V2 handoff URL. Do not drive V2 from V4 tests.
- Reasonable timeouts: actions 15s, navigation 30s, expect 10s. The editor is slower than you expect.
