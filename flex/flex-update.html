🎯Dynamic testing that scales with the product

The tests are agentic — they adapt to each facility's layout and content dynamically. Onboarding a new facility or a new Flex client takes one config entry, and the full customer journey is verified automatically:

Flex facility page → Browse units → Click Rent Now → V2 SPC /step-four → "24 Hour Access" add-on → Tenant + Payment → hCaptcha → Submit

The checks aren't surface-level. We're not just asking "does it render" — we ask things like: is web rate ≤ standard rate on every dual-priced unit? Does every Rent Now URL hand off to V2 with a valid unit_id? Are unit IDs unique across cards? Does clicking Next on the carousel actually advance the slide?

🧭Config-driven verifications

Every test uses semantic locators (button by role + visible text, never CSS classes), so when designers update the editor template, the tests don't break. The product is becoming the configuration — the tests verify the configuration end-to-end.

Two key outcomes from this approach:

  • Layout-tolerant. Different facilities ship different layouts and different visible components. The same test passes on all of them as long as the customer journey works.
  • Config-driven. flex/configs/facilities.ts is the source of truth. Adding the next Safeguard facility — or a brand new Flex client — is one line of config. No code.

♻Modular architecture — reuse over reinvention

We did not rebuild SPC checkout for Flex. The RentalDetailsPage_SPC page object that runs for every storEDGE, SiteLink, SSM, and Yardi client is the same one that handles Safeguard now. We added one small hook and wired it via a per-client config:

const SPC_CONFIG_BY_CLIENT = {
  safeguard: {
    addons: ['24 Hour Access'],   // recommended add-on, toggled before payment
    captchaAtRentNow: true,         // hCaptcha after RENT NOW click — manual solve
    captchaAtStepFour: false,
  },
};

hCaptcha handling is wired identically to every other captcha client — same audible alert, same auto-detect on solve, same no-timeout pattern. No duplicated test logic anywhere. Future Flex clients with different add-ons or no captcha = same pattern, different values.

The entire framework — from architecture to test logic to reporting — was built with an AI-first, agentic development workflow, consistent with the direction the company is moving. The result is faster iteration, tighter feedback loops, and a QA layer that evolves at the same speed as the product.

→Roadmap

Planned coverage areas, ranked by customer impact:

  1. 1.Broken link detection — verify every navigation and footer link resolves to a live page. Catches renamed routes before customers hit a dead end.
  2. 2.Unit sorting verification — customer selects "Price: Low to High" and the displayed units actually reorder correctly.
  3. 3.Unit filtering verification — customer toggles a filter like Climate-Controlled and only matching units remain visible.
  4. 4.Mobile experience — re-run all section checks at mobile viewport widths to catch responsive layout issues before customers on phones do.
  5. 5.Pricing logic validation — verify promo rates, dual-pricing rules, and discount displays are consistent across units and facilities.
  6. 6.Authoring component verification — validate that each editor component renders correctly on the published site after authoring.
  7. 7.Template-based verification — ensure template tokens resolve properly across different facility configurations.
  8. 8.Pre-deploy staging coverage — when a staging environment is available, the same suite runs against it before production. Env-switching is already built in.
